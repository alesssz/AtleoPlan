# P1. Conventions

How work is done in this repository: Git, code, comments, documentation and the backlog. They follow Chronovault's conventions, adapted to Laravel and React.

## P1.1 Git

- **One branch per task** from `main`, with a short English name and a type prefix: `feat/plan-editor`, `fix/rest-timer`, `docs/ui-design`, `chore/docker`. `make branch name=feat/plan-editor` creates it from an up-to-date `main`.
- **Commit messages** in English, imperative, one subject line (`Add the rest timer to workout mode`), a body when the why is not obvious.
- **Identity:** commits use the same personal GitHub identity as Chronovault, set in this repository's own `.git/config`; a computer's global Git configuration (on the work Mac, the work identity) is never used here.
- **No real email in the history:** author and committer are always the GitHub noreply address, so the repository can become public as it is. The `pre-commit` hook in `.githooks/` refuses any other identity; a new clone turns it on with `git config core.hooksPath .githooks` ([S1.3](../start/S1-setup.md#s13-git-identity)).
- Merges into `main` keep a merge commit (`--no-ff`), so each branch stays readable in the history.
- **Merging is done with `make merge`** ([`scripts/merge-main.mjs`](../../scripts/merge-main.mjs), the same as Chronovault's), from the branch, once it is pushed (`make push`). It stops if the branch is not ready (uncommitted or unpushed work, nothing new), runs `make check`, shows the commits and asks; then it updates `main`, merges with a message listing the branch's commits, pushes `main`, deletes the branch on GitHub and locally, and leaves you on `main` in sync. A conflict is aborted and you are back on the branch. `yes=1` skips the question, `checks=0` the checks (for a docs-only branch).

## P1.2 Code

- **Language:** everything in the repository is in English: code, comments, docs, commit messages. The interface's texts are in translation files, one per language (Italian, English, Spanish, German), never written in a component ([D2.4](../design/D2-decisions.md#d24-languages)).
- **Comments, in depth, for a reader new to the stack.** Comments are written for someone who knows little Laravel, PHP or React and reads the code to learn it. Beyond what a line does, they name and explain the concept behind it the first time it appears in a file (a migration, a facade, an Eloquent model, a hook, JSX, a provider…) and point to the guide that explains it at length ([C1. Frontend](../concepts/C1-frontend.md), [C2. Backend](../concepts/C2-backend.md)). Files generated by Laravel or shadcn/ui get the same treatment once they are part of the code.
  - Every file starts with what it is for and how it fits in (a PHP docblock at the top of the class, a block comment at the top of a TypeScript file).
  - Every class, function, React component, hook, exported constant, prop and type field has a doc comment (PHPDoc / TSDoc).
  - Every local constant or variable gets a short line saying what it holds; one line may cover a group that belongs together.
  - Non-obvious lines explain *why*, not *what*.
  - The main blocks of JSX are labelled (`{/* Rest timer bar */}`), and Blade / Filament views likewise.
  - Tests describe their fixtures and scenarios.
  - Migrations get comments explaining each table and column; once applied, a migration never changes: a change is a new migration.
- **Style:**
  - PHP: **Laravel Pint** with the `laravel` preset.
  - TypeScript: **ESLint** with stylistic rules (`@stylistic/eslint-plugin`), as in Chronovault: 2 spaces, no semicolons, single quotes; no Prettier. VS Code fixes on save; `make fix` fixes everything, files generated by shadcn/ui included. File naming and structure of the frontend: [C1.2](../concepts/C1-frontend.md#c12-folder-structure).
- **A new API endpoint:** the controller only authorises (a policy), validates (a Form Request) and calls an action or service; the rules live in the service, tested without HTTP; the answer is an API Resource. Every route is covered by a Pest test, the forbidden cases included (another user's plan, a public exercise edited by a non-admin).
- **A new table or column:** [D3. Data model](../design/D3-data-model.md) first, then migration (commented) → model (casts, relations) → policy → factory → tests → API Resource → the frontend's API types. The commands and each step: [H1.2](../how-to/H1-database.md#h12-a-new-table-from-start-to-finish).
- **Identifiers created on the device** (plans, sessions, logged sets: the full list is in [D3.2](../design/D3-data-model.md#d32-rules-for-every-table)) are UUIDs, and the endpoints that receive them are idempotent ([D2.7](../design/D2-decisions.md#d27-offline-and-sync)).
- **Icon-only buttons** always have a label, which is also their tooltip: mouse users see what screen readers hear ([D1.7](../design/D1-ui.md#d17-responsive-layout-and-accessibility)).
- **Never** put credentials (storage keys, API tokens) in client code or in Git; they live in `.env`, which is not committed (`.env.example` is, with every variable and no secrets).

## P1.3 Documentation

- **`README.md`** holds only the introduction, a short quick start and a map of the folders; everything else is in `docs/`, whose index is [`docs/README.md`](../README.md).
- **Folders by purpose,** each with a letter:
  - `start/` (S): installing and starting;
  - `design/` (D): what the app does and why;
  - `concepts/` (C): how the code works;
  - `how-to/` (H): doing things step by step;
  - `project/` (P): how we work, and the backlog;
  - `learn/` (L): courses on the frameworks themselves, standard Laravel and React, lesson by lesson. A course keeps apart what is the framework, what is a package and what is our choice; its examples are run for real, like the how-tos.

  A document's code is its folder's letter and a number from 1, which is also the start of its file name: `docs/how-to/H2-backend.md` is H2.
- **A change updates the section it touches, in the same commit.** A change to how the project is installed or started also updates the setup section, once it exists.
- **Every task comes with its "how to".** Saying what was built is not enough: the docs must also say how it was done, so that the next one can be done by hand. The how-to goes in the how-to guide for the area: [H1. Database](../how-to/H1-database.md), [H2. Backend](../how-to/H2-backend.md), [H3. Frontend](../how-to/H3-frontend.md), or a new section when none fits. [C1. Frontend](../concepts/C1-frontend.md) and [C2. Backend](../concepts/C2-backend.md) keep the explanation of how things work. It covers:
  - the commands that were run, in order, with their real output;
  - the files created or changed, and what goes in each;
  - how to check the result: in the browser, in tinker, with a test;
  - the errors met along the way, and their fix.

  When a guide already explains that kind of work, the task adds only what is new. The model to follow is [H1.2](../how-to/H1-database.md#h12-a-new-table-from-start-to-finish).
- **Every document opens with a "Contents" list** of its sections, generated from the headings by [`scripts/docs-toc.mjs`](../../scripts/docs-toc.mjs). After adding, renaming or removing a heading, run `make toc`; never edit the list by hand. `make check` fails when a list is out of date.
- **Headings carry the document's code** (`## H2.3 An endpoint that changes data`) and keep their numbers. References give them ("see D1.4.9"), in the docs and in code comments: `// Warm-up sets are excluded (docs/design/D2-decisions.md D2.8)`.
- **A new document** goes in the folder that fits its purpose, with the next free number of that folder (the next how-to is `docs/how-to/H4-name.md`). It needs a row in [`docs/README.md`](../README.md), and the navigation lines at the bottom of the previous and next pages. Numbers are never reused, so a reference never points to the wrong document.
- **Setup** ([S1](../start/S1-setup.md)) follows the project: a new service, port, command or prerequisite updates it in the same commit.
- Sections still to come, as the code is written: architecture, project structure, data flows, security, API reference, configuration, testing, deployment, troubleshooting.

## P1.4 Backlog

Work known and waiting goes in [`docs/project/backlog.md`](backlog.md), one entry per point with an ID (`UI-5`, `FEAT-1`) that is never reused. The branch that does a point deletes its entry in the same commit; a point found along the way that does not belong to the branch gets an entry instead of a fix on the side.
